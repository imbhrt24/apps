Buttons

A button is a promise: press this and something happens now. You already check its contrast and its size. There are ten more things to check, and every one is a design decision, not a developer's.

Contrast, for the label and the shape

You know text needs contrast. The parts people miss: the required number changes with text size, and the icon and the outline of the button itself need contrast too, or people can't tell there is a button there.

Label 6.5 : 1. The border is strong enough to say "this is a control".

Check three pairs for every button style: label against fill (4.5 : 1), icon against fill (3 : 1), and for outline or ghost buttons the border against the page (3 : 1). Repeat for hover, pressed and dark mode.

WCAG 1.4.3 Contrast (Minimum), AA: 4.5 : 1 for text, 3 : 1 for large text (24px and up, or about 19px bold). WCAG 1.4.11 Non-text Contrast, AA: 3 : 1 for icons and for whatever visually identifies the control and its state. Disabled buttons are exempt, but should still be readable.

Target size, and the gap between targets

A button someone cannot hit is a button that does not work: a shaking hand, a thumb on a bus, a trackpad in a hurry. Size is half of it. The other half is the gap, because a miss should land on nothing, not on Delete.

20 × 20 px, touching

Edit, Copy and Delete share one fingertip. A slip deletes the row.

40 × 40 px, 10 px apart

Same icons. The tap area is larger than the icon, and Delete sits apart.

The tap area can be bigger than what you draw. Put a 44 px frame around a 20 px icon and note "hit area 44 × 44" in the spec. Keep destructive actions away from frequent ones.

WCAG 2.5.8 Target Size (Minimum), AA: 24 × 24 CSS px, or enough spacing that a 24 px circle on each target does not overlap another. WCAG 2.5.5 (AAA) asks for 44 × 44. Apple recommends 44 pt, Material 48 dp.

What you're probably missing

These six never show up in a static mockup. You only notice them with a keyboard, a screen reader or a different pair of eyes.

Every icon needs a name

A screen reader cannot see a bin icon. It reads the button's name, and an icon alone has none. To that user, three icon buttons in a row are "button, button, button".

Three icons, no names.

Same icons, each with a name the eye never sees.

Press Tab through both rows and read the dark strip. Both rows look identical to you. Only one tells a blind user what the button does.

You choose the name, not the developer. Add a line per icon button: "Bin icon, name: Delete". If it has a tooltip, the name and the tooltip should say the same thing.

WCAG 4.1.2 Name, Role, Value (A). Developers add the name with aria-label or visually hidden text inside the button.

A label that makes sense on its own

Screen reader users often pull up a list of every button on the page. In that list, "OK", "Submit" and "Click here" mean nothing. Voice control users say the label out loud, so "Click Send invoice" must match the words on screen.

Write labels as verb plus object. Read your buttons as a bare list with the layout hidden. If you cannot tell what each does, rewrite it.

WCAG 2.4.6 Headings and Labels (AA) and 2.5.3 Label in Name (A): the coded name must contain the visible label, so voice commands work.

A focus state you can actually see

Keyboard users move with Tab. The focus ring is their cursor. Remove it "because it looks cleaner" and you have hidden the mouse pointer for everyone who does not use a mouse.

Focus ring removed. Nothing replaces it.

A 3 px ring with a small gap, visible on any colour.

Press Tab through the left row and try to say which button you are on. Then do the same on the right.

Add "focus" as a variant on every interactive component, next to hover and pressed. Test the ring on white, on colour and on images. Also check that sticky headers and footers never cover the focused button.

WCAG 2.4.7 Focus Visible (AA). WCAG 2.4.11 Focus Not Obscured (AA): the focused control must not be fully hidden by sticky content. WCAG 2.4.13 Focus Appearance (AAA) is the best target to design to: at least 2 px thick, 3 : 1 against the unfocused state.

It works without a mouse

Looking like a button and being a button are different things. A real button is reached with Tab and pressed with Enter or Space. A styled box with a click attached works for a mouse and for nobody else.

A "clickable" box

Click it with a mouse and it works. Tab skips it completely.

A real button

Reachable, pressable, and it reports its state.

Tab toward both hearts. Focus never lands on the left one. On the right one, press Space or Enter.

In handoff, call it "a button", never "a clickable container". If you invent a custom control, write down which keys operate it.

WCAG 2.1.1 Keyboard (A). Built with a native <button>, keyboard support comes for free.

State shown by more than colour

About 1 in 12 men and 1 in 200 women have some form of colour blindness, most often red and green. If success and failure differ only by hue, those users see two identical buttons.

Turn your frame to greyscale. If two states become identical, add an icon, a word, or a shape change.

WCAG 1.4.1 Use of Color (A).

Every state, especially loading

A button has more states than default and hover: focus, pressed, loading, success, error, disabled. Loading is the one that fails silently. A spinner alone tells a screen reader nothing, and tells everyone else "maybe press it again".

The label is replaced by a spinner. Nothing is announced.

Words change to "Saving…", then "Saved", and both are announced.

Build the full state set as variants. For loading, write the exact words ("Saving…", "Saved") and note "announce this to screen readers".

WCAG 4.1.3 Status Messages (AA): changes that do not move focus must still be announced. Developers use a live region, and block repeat presses while the request runs.

Senior-level traps

Each button below passes every check above on its own. The problem only appears once it sits in a real screen.

The disabled button that never says why

Greying out "Continue" until the form is perfect feels tidy. In use, people stare at a dead button with no idea what is wrong. Keyboard focus skips it entirely, and it usually fails contrast as well.

Tab goes from the field straight out of the form. The button is never reached.

Enter your work email to continue

The button stays live. Pressing it tells you exactly what is missing.

Default to an enabled button plus a clear error. If a button truly must be disabled, put the reason in visible text next to it ("Add at least one item to continue").

Not a single WCAG criterion, but it touches 3.3.1 Error Identification (A) and 3.3.2 Labels or Instructions (A). If the control must stay focusable while unavailable, developers use aria-disabled="true" instead of disabled.

Button or link? You decide, not the developer

A button does something here. A link takes you somewhere. They can look identical, but they behave differently: links open in a new tab, can be copied and bookmarked, and are announced as "link". Mark it wrong and all of that breaks.

Goes to another page, but is built as a button. No "open in new tab", and it is announced as an action.

View pricing

Looks the same. It is a link, so right-click, new tab and "link" all work.

Ask one question: does the address in the browser change? If yes it is a link, however it is styled. Tag each one in your spec.

WCAG 4.1.2 Name, Role, Value (A). Navigation uses <a href>, actions use <button>.

Delete, Delete, Delete

In a list, every row has the same button. You can see which row each one belongs to. A screen reader user hearing "Delete, button" has no idea what they are about to destroy.

WCAG 2.4.6 Headings and Labels (AA) and 4.1.2 (A). Developers add the row name to the accessible name, keeping the visible word at the start so voice control still works.

A clickable card with buttons inside it

Making the whole card clickable and putting a button inside it creates a target within a target. A tap near the heart may open the card. A screen reader reads the entire card as one giant link name.

Whole card is one click area
Project Falcon12 tasks, due Friday
Title is the link

Give a card one main link, usually the title. Keep other actions as separate buttons with their own space. Draw the two hit areas so nobody guesses.

Interactive elements must not be nested inside each other (HTML rule, and WCAG 4.1.2). Developers can stretch the title link over the card visually while keeping the buttons separate.
