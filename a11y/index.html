Welcome

Accessibility, by example

Most accessibility guidance is written for engineers — ARIA attributes, contrast ratios, code snippets. This is written for the person who decides what the button says, where the modal opens, and how the table is laid out. Every idea here is something you can feel with your own keyboard, not just read about.

How each page works

Every component has two views. The Component covers getting the thing itself right — its label, its focus state, its size. In Use covers what happens when that component is dropped into a real product screen — a table inside a modal, a nested table inside a row — where most accessibility actually breaks down, especially in dense enterprise products.

Cards tagged Live demo are real, working UI. Put your mouse away and press Tab — you'll notice the difference yourself. Cards tagged Annotated walk through the same do/don't logic visually. Every card has a small "the rule, for handoff" note you can open when you need the exact language to give an engineer.

Component

Buttons

A button is a promise: press this, and something happens right now. Almost every accessibility failure in a button comes down to one question — can a person who can't see or point at it still tell what it does, and still reach it?

Label clarity

Live demo

An icon alone means nothing to a screen reader unless it's given a name. If the label only exists visually, half your users never receive it.

✕ Avoid

Three icon buttons, no accessible name.

🔊Tab to a button…
✓ Do

Same icons, each with an aria-label.

🔊Tab to a button…

Try it: press Tab into both rows. Every icon looks equally clear to you — but only one row tells a screen-reader user what it's about to do.

The rule, for handoff
WCAG 4.1.2 (Name, Role, Value) and 2.5.3 (Label in Name). Give icon-only buttons an aria-label, and make sure it matches or contains any visible tooltip text.

A focus state you can actually see

Live demo

If you can't see where focus is, you can't use the interface without a mouse. Removing the focus outline for "cleanliness" removes the interface for keyboard users.

✕ Avoid

outline: none with nothing to replace it.

✓ Do

A clear ring on every stop, 3px, high contrast.

Try it: click the first button in each row, then press Tab twice. In the left row, focus is invisible — you're using the interface blind.

The rule, for handoff
WCAG 2.4.7 (Focus Visible) and 2.4.11 (Focus Appearance, AA). Never remove the focus indicator without providing one at least as visible — a 2px+ outline with 3:1 contrast against its background.

Target size and spacing

Annotated

A button someone can't accurately tap or click is a button that doesn't work — for shaky hands, big thumbs, or anyone in a hurry.

✕ Avoid
  • 118–22px targets packed edge to edge — easy to miss or mis-tap.
✓ Do
  • 1Minimum 24×24px hit area (44px on touch), with breathing room between.
The rule, for handoff
WCAG 2.5.8 (Target Size Minimum, AA): 24×24px CSS pixels minimum, or adequate spacing to an equivalent effect. Aim for 44×44px on touch surfaces.

State shown by more than color

Annotated

Roughly 1 in 12 men can't reliably distinguish red from green. If "saved" and "failed" only differ by hue, that group can't tell them apart.

✕ Avoid
  • 1Error vs. success communicated by color alone.
✓ Do
  • 1Icon + text carries the meaning; color reinforces it.
The rule, for handoff
WCAG 1.4.1 (Use of Color). Pair every color-coded state with an icon or text label.

Disabled buttons

Live demo

A truly disabled button is invisible to Tab and to screen readers — nobody can find out why it's off, or when it'll turn on. If people need to understand why, keep it focusable instead.

✕ Avoid

Real disabled attribute — unreachable, unexplained.

🔊Tab through…
✓ Do

aria-disabled — stays reachable, explains itself.

🔊Tab through…

Try it: Tab through both rows. On the left, Tab jumps straight past "Continue" as if it doesn't exist — a keyboard user won't even know it's there, let alone why it's off.

The rule, for handoff
Use native disabled only for actions nobody needs an explanation for. Otherwise use aria-disabled="true" (element stays in tab order, click handler no-ops) plus visible reason text.

Button vs. link

Live demo

This is a design decision, not a dev one: does this control do something on this screen (button) or take you somewhere else (link)? Get it wrong and keyboard shortcuts, right-click-open-in-new-tab, and screen-reader navigation all break.

✕ Avoid
Go to Settings

A styled <span> with a click handler — not reachable by Tab at all.

🔊Tab to it…
✓ Do
Go to Settings

A real <a> — focusable, opens in new tab, announced as a link.

🔊Tab to it…

Try it: Tab toward each demo. The left one is skipped entirely — a mouse-only control masquerading as navigation.

The rule, for handoff
Navigation → <a href>. In-page action → <button>. Never build interactive controls from a <div> or <span>.

Icon-only toolbars

Annotated

A dense toolbar (formatting, media controls, dashboard actions) is often only icons — the exact case where every single one needs a name, and where a "current tool" state needs to be announced too.

✕ Avoid
  • 1No labels, and the "active" formatting state (e.g. Bold is on) isn't exposed at all.
✓ Do
  • 1Each has aria-label; active ones use aria-pressed.
The rule, for handoff
Toolbar buttons need aria-label and, if the toolbar is a single logical group, consider a role="toolbar" wrapper so arrow keys move between them.

Toggle buttons & segmented controls

Live demo

A toggle that only changes color when pressed tells a sighted mouse user it's "on" — and tells a screen-reader user nothing at all, unless its pressed state is exposed in code.

✕ Avoid

Color flips on click; state lives only in CSS.

🔊Focus, then press Enter…
✓ Do

aria-pressed flips with the visual state.

🔊Focus, then press Enter…

Try it: Tab to each button and press Enter a couple of times — watch the caption on the right actually announce "pressed."

The rule, for handoff
Use aria-pressed="true|false" on toggle buttons, and aria-selected for one-of-many segmented controls with role="radiogroup"/radio semantics.

Disabled-until-valid submit

Annotated

Locking "Submit" until a form is perfect gives no one — sighted or not — any idea what's still wrong. It just feels broken.

✕ Avoid
  • 1Button silently stays off. No error, no hint why.
✓ Do
Enter a valid email to continue
  • 1Button stays enabled; pressing it surfaces exactly what's missing.
The rule, for handoff
Keep submit enabled and validate on submit (or on blur) with inline, programmatically-associated error text (aria-describedby).

Repeated row actions

Live demo

A screen reader lists all the buttons on a page as one flat set. Ten rows each with a "Delete" button announce as "Delete, Delete, Delete…" — nobody can tell which row they're about to destroy.

✕ Avoid
Acme Corp invoice
Globex invoice
🔊Tab to a Delete…
✓ Do
Acme Corp invoice
Globex invoice
🔊Tab to a Delete…

Try it: Tab to each Delete button and read the caption — only one row tells you what you're deleting before you commit.

The rule, for handoff
Add a visually-hidden suffix or aria-label="Delete {{row name}}" so the accessible name is unique per row.

Destructive actions — confirm and undo

Annotated

A confirmation dialog worded "Are you sure?" tells nobody what they're confirming. And a screen-reader or motor-impaired user benefits enormously from a generous "undo" window over a blocking confirm.

✕ Avoid

Are you sure?

This can't be undone.

  • 1Vague wording; "Yes/No" forces re-reading the whole dialog to know which is which.
✓ Do

Delete "Q3 Report"?

This file will be removed from all shared folders.

  • 1Buttons restate the actual action, not generic Yes/No.
The rule, for handoff
Button labels should restate the action ("Delete file", not "Yes"). Prefer inline undo over a blocking confirm where the action is reversible.

Async / loading buttons

Annotated

A silent spinner tells a screen-reader user nothing changed — and invites a second, duplicate click.

✕ Avoid
  • 1Spinner has no text alternative; button stays clickable mid-request.
✓ Do
🔊Saving, please wait
  • 1Visible "Saving…" text, an aria-live status update, and the button can't double-fire.
The rule, for handoff
Swap the label to a verb + ellipsis, disable (or aria-disabled) during the request, and post progress to an aria-live="polite" region.

Split buttons & dropdown buttons

Annotated

A button that's secretly two controls glued together (a default action + a chevron menu) needs two separately reachable, separately named targets — not one big blob.

✕ Avoid
  • 1One button, one Tab stop — the chevron's menu is unreachable by keyboard.
✓ Do
  • 1Two real buttons; the second uses aria-haspopup and its own label.
The rule, for handoff
Build split buttons as two adjacent <button> elements. The menu trigger gets aria-haspopup="menu" and aria-expanded.

Clickable cards vs. buttons inside them

Annotated

A card that's clickable and contains its own buttons creates nested interactive zones — a screen reader or keyboard user can't tell where the card's click target ends and the inner button begins.

✕ Avoid
Project Falcon
  • 1The whole card and the "⋯" button both fire click — one nested inside the other.
✓ Do
Project Falcon
  • 1Only the title is the link; the menu button is a clearly separate, sibling control.
The rule, for handoff
Never nest interactive elements. Make the card's primary link one clear target (often the title) and keep secondary actions as visually-distinct sibling buttons.

Sticky CTAs & floating action buttons

Annotated

A button pinned to the viewport can permanently cover content underneath once someone zooms in — especially at 200%+ text size, which WCAG requires your layout to survive.

✕ Avoid

Line one of body copy that keeps going and going under the button…

  • 1At high zoom the FAB permanently overlaps the last lines of content.
✓ Do

Body copy reserves space so the sticky bar never overlaps it, at any zoom level.

  • 1Content has reserved padding equal to the sticky element's height.
The rule, for handoff
WCAG 1.4.10 (Reflow). Reserve layout space for fixed/sticky elements so they never permanently obscure content at 400% zoom.

Button vs. link in marketing heroes

Annotated

"Get started" that navigates to a pricing page is a link dressed as a button — which breaks right-click → open in new tab, a habit many power users rely on constantly.

✕ Avoid
  • 1Styled like a button, implemented with an onClick that changes window.location.
✓ Do
Get started →
  • 1Same visual weight, real <a href> underneath.
The rule, for handoff
If pressing it changes the URL, it must be an anchor tag — styling can still look exactly like a button.

Modals

A modal interrupts the entire page to demand attention on one task. That's exactly why it's high-risk: focus, keyboard trapping, and return-of-focus all have to be handled correctly, or a keyboard user can get lost — or trapped — behind the page.

The focus lifecycle

Live demo — flagship

A correct modal does four things in order: moves focus into itself on open, traps Tab so it can't reach the page behind, closes on Escape, and returns focus to whatever opened it. Miss any one of these and a keyboard user gets lost or stuck.

✕ Avoid

Focus doesn't move on open, and Tab escapes to the page behind.

✓ Do

Focus enters, stays trapped, Esc closes, focus returns here.

Try it: open the left modal, then press Tab repeatedly — you'll land back on this page's nav and buttons while the modal is still open, invisible and unusable. Now open the right one: Tab loops forever inside it, and Escape (or Close) sends focus right back to the button you started on.

The rule, for handoff
WCAG 2.4.3 (Focus Order) and 2.1.2 (No Keyboard Trap, inverted — the modal is the one legitimate trap). On open: move focus to the modal (usually its heading or first field). While open: keep Tab/Shift+Tab cycling only within it. On close: return focus to the trigger element.

An announced title

Annotated

The instant a modal opens, a screen-reader user should hear what it's for — without having to explore it first.

✕ Avoid
role="dialog" — no name
  • 1Opens silently: "dialog" and nothing else.
✓ Do
role="dialog" aria-labelledby="title"
  • 1Announces: "Delete file, dialog."
The rule, for handoff
Give the dialog container role="dialog" (or alertdialog for warnings) and aria-labelledby pointing at its visible heading.

The background is made inert

Annotated

If the page behind the modal is still "live," a screen-reader user exploring by swipe can wander straight into it without knowing a modal is open.

✕ Avoid
Modal open, page content behind still reachable by swipe/Tab.
  • 1Background isn't hidden from assistive tech.
✓ Do
Background marked inert / aria-hidden while modal is open.
  • 1Only the modal exists, as far as assistive tech is concerned.
The rule, for handoff
Apply the inert attribute (or aria-hidden="true" on all siblings) to everything outside the modal while it's open.

A real, visible close control

Annotated

If the only way out is clicking the dim backdrop, anyone navigating by keyboard or screen reader has no idea that's even an exit.

✕ Avoid
No visible close button — backdrop click only.
  • 1No discoverable, focusable exit.
✓ Do
Modal title
  • 1Labeled, focusable close button, plus Escape.
The rule, for handoff
Always include a focusable, labeled close button in addition to Escape — never rely on backdrop click as the only exit.

Complex forms inside a modal

Live demo — flagship

This is the pattern you flagged, and it's everywhere in enterprise tools: a long form crammed into a small overlay. The moment it needs to scroll, or throws a validation error, the modal loses two things a full page never gives up — a stable frame of reference, and room to see the rest of the product for context.

✕ Avoid

7-field form squeezed into a 480px box.

✓ Do instead
→ A dedicated page or a full-height side panel, with the same form given room to breathe and its own URL.

Try it: open the modal and press Tab through every field, then submit it empty. Notice you can't see the page behind for reference, and once it's scrolled, the title and close button may have scrolled off too.

The rule, for handoff
If a form has more than ~4 fields, needs its own scroll, or people need to reference the page behind while filling it in — it should not be a modal. Use a full page or a persistent side panel instead.

Data tables inside a modal

Live demo — flagship

Also from your own experience: enterprise products love putting a data table inside a modal ("view details," "select from list"). The table needs to scroll sideways; the modal needs to scroll up and down — now there are two competing scroll zones stacked on top of each other, which is disorienting for everyone and often unusable with a screen reader or on a small screen.

✕ Avoid

Wide table, narrow modal — double scrollbars.

✓ Do instead
→ A full page or drawer with the table given the whole viewport width, or a simplified single-column "picker" list instead of the full table.

Try it: open the modal and try to see every column — you'll need to scroll the table horizontally and the modal vertically, in a space smaller than your screen.

The rule, for handoff
Nested independent scroll regions are a known WCAG 1.4.10 (Reflow) and usability risk. If a table needs its own horizontal scroll, it shouldn't be nested inside a vertically-scrolling container.

Stacked modals

Annotated

A modal that opens another modal on top doubles every focus-trap and return-focus problem — and most implementations only ever built the logic for one layer.

✕ Avoid
Modal B opens over Modal A; closing B returns focus to Modal A's trigger — a button now hidden behind Modal A itself.
  • 1Focus returns to a now-invisible element.
✓ Do
Avoid stacking at all — replace Modal A's content in place, or use a single wizard-style modal with steps.
  • 1One modal, one focus trap, one return path.
The rule, for handoff
Avoid modal-over-modal. If unavoidable, each layer needs its own independent focus trap and must return focus to the correct still-visible trigger.

Confirmation dialogs

Annotated

The default-focused button in a confirm dialog is whichever one gets triggered by an accidental Enter press — so it should almost never be the destructive one.

✕ Avoid
  • 1Initial focus defaults to the destructive action.
✓ Do
  • 1Initial focus defaults to the safe action.
The rule, for handoff
Default focus goes to the non-destructive option, unless the destructive action is what the user just explicitly asked to confirm.

Alert dialogs & session timeouts

Annotated

A session-timeout warning that appears silently and vanishes after 10 seconds can log someone out mid-task without them ever knowing it appeared.

✕ Avoid
Toast fades in top-right, auto-dismisses in 10s, no sound or focus change.
  • 1Easy to miss entirely; timer keeps running regardless.
✓ Do
role="alertdialog", interrupts and requests focus, stays until dismissed, offers "Stay signed in."
  • 1Impossible to miss; user controls when it closes.
The rule, for handoff
Time-critical alerts use role="alertdialog", take focus immediately, and never auto-dismiss on their own timer (WCAG 2.2.1, Timing Adjustable).

Click-outside-to-dismiss on data entry

Annotated

Dismissing a half-filled form with a single accidental click outside the box is one of the most common ways people lose work.

✕ Avoid
Any click on the backdrop instantly closes the form — no warning.
  • 1One misclick, work gone.
✓ Do
Backdrop click on a dirty form triggers "Discard changes?" — or is disabled entirely once the form has input.
  • 1Accidental dismissal is caught before data is lost.
The rule, for handoff
Track dirty state; once a user has entered data, require an explicit confirm before backdrop-dismiss or Escape closes the modal.

Multi-step wizards inside modals

Annotated

Each step change inside a modal is effectively a new "page" — if focus and headings don't reset per step, a screen-reader user can't tell they moved at all.

✕ Avoid
Step 2 content swaps in silently; focus stays wherever it was on Step 1.
  • 1No announcement that the step changed.
✓ Do
On step change, move focus to the new step's heading; heading text updates ("Step 2 of 3: Billing").
  • 1Step change is announced and focus lands in the right place.
The rule, for handoff
Move focus to each new step's heading on transition, and include "Step X of Y" in that heading's accessible name.

Side panel / drawer as the alternative

Annotated

Most of the modal failures above share one fix: don't use a modal. A side panel keeps the page behind visible and scrollable independently, while still focusing attention on the task.

✕ Avoid
Long form or table forced into a centered 480px modal.
  • 1Fixed small footprint regardless of content.
✓ Do
Full-height drawer sliding from the edge, its own independent scroll, page behind still visible and dimmed (not hidden).
  • 1Same focus-trap rules apply, but content has real room.
The rule, for handoff
Drawers still need the full focus lifecycle (trap, Escape, return-focus) — swapping the shape doesn't remove those requirements.

Full-screen modals on mobile

Annotated

A centered 480px modal on a 375px phone screen either overflows or gets crushed — on mobile, a modal should almost always become full-screen.

✕ Avoid
Fixed-width desktop modal shrunk to fit — tiny tap targets, cramped text.
  • 1Desktop layout ported unchanged to a small viewport.
✓ Do
Full-screen sheet with a top bar (Close + title), content fills the viewport, no competing scroll region.
  • 1Uses the full viewport; one scroll region, generous targets.
The rule, for handoff
Below ~600px viewport width, modals should expand to fill the screen rather than float as a small centered card.

Lightbox / media modals

Annotated

An image lightbox often ships with zero keyboard support — arrow keys don't move between images, and there's no accessible name for what's currently showing.

✕ Avoid
Image swaps on click of tiny, unlabeled arrow icons; no caption or alt text surfaced.
  • 1Mouse-only navigation, no announced content.
✓ Do
Left/Right arrow keys navigate; "Image 2 of 8: [description]" is announced; labeled Next/Previous buttons.
  • 1Full keyboard support and a real accessible name per image.
The rule, for handoff
Support Left/Right arrow keys, label Next/Previous controls, and update an aria-live region or the dialog's accessible name with position and description on each change.

Auto-opening popups & interstitials

Annotated

A modal that opens itself — a newsletter signup, a survey — steals focus from whatever someone was mid-task doing, with zero warning.

✕ Avoid
Fires automatically 3 seconds after page load, focus is yanked from wherever it was.
  • 1Unrequested interruption to whatever the user was doing.
✓ Do
Triggered only by a user action (scroll-to-end, exit intent with a clear affordance), or shown as a dismissible inline banner instead.
  • 1User-initiated, or non-blocking.
The rule, for handoff
Avoid unsolicited focus changes (WCAG 3.2.1/3.2.5, On Focus / Change on Request). If a promo must appear automatically, prefer a non-modal, easily dismissible banner over a focus-stealing dialog.

Tables

A sighted user scans a table with their eyes, jumping between rows and columns freely. A screen reader can only read it one cell at a time — which means the table's structure, not just its content, has to carry the meaning.

Header cells that describe the column

Live demo

Move through a table cell by cell with a screen reader, and it re-announces the column header each time — but only if the header is marked up as one.

✕ Avoid
NameStatus
Acme CorpActive

Header row built from plain <td>.

🔊Focus a data cell…
✓ Do
NameStatus
Acme CorpActive

Real <th scope="col">.

🔊Focus a data cell…

Try it: Tab to a data cell in each table. Only the right one tells you which column you landed in.

The rule, for handoff
WCAG 1.3.1 (Info and Relationships). Use real <th scope="col">/scope="row", never a styled <td>, for anything that labels a row or column.

Row selection & bulk-action bars

Annotated

A checkbox with no visible label relies entirely on position to make sense — which breaks the moment it's read out of visual context.

✕ Avoid
Acme Corp
  • 1Checkbox announces only as "checkbox, not checked" — select what?
✓ Do
Acme Corp
  • 1"Select Acme Corp, checkbox" — row identity included in the name.
The rule, for handoff
Each row checkbox needs aria-label="Select {{row name}}", and the resulting bulk-action bar should announce the current selection count via aria-live.

Hover-only row actions

Live demo

Actions that only appear on mouse hover are invisible to anyone navigating by keyboard — they need to appear on keyboard focus too.

✕ Avoid
Acme Corp

CSS uses :hover only — Tab-focusing the button doesn't reveal it.

✓ Do
Acme Corp

Uses :hover, :focus-within — Tab reveals it too.

Try it: Tab through both rows without touching your mouse — only the right-hand action button becomes visible as focus reaches it.

The rule, for handoff
Any CSS rule that reveals content on :hover must also trigger on :focus-within or :focus-visible.

Inline editing / editable grids

Annotated

A cell that silently becomes an input on double-click has no discoverable way in for a keyboard-only user — and no obvious way to tell it's now editable.

✕ Avoid
Acme Corp
  • 1Double-click only; nothing indicates the cell is editable.
✓ Do
  • 1Enter/Space opens edit mode from keyboard focus; visible edit affordance.
The rule, for handoff
Editable cells need a keyboard-operable trigger (Enter to edit, Escape to cancel, Enter/blur to save) and a visible affordance showing they're editable.

Sorting & filtering controls

Annotated

Filters that live in a hidden flyout with no labels reduce a whole table to guesswork about what's currently applied.

✕ Avoid
Filter icon opens an unlabeled panel; active filters shown only as colored dots.
  • 1No text summary of what's currently filtered.
✓ Do
Status: Active ✕
  • 1Applied filters shown as removable, labeled chips above the table.
The rule, for handoff
Surface active filters as text (chips or a summary line), each individually labeled and removable — see also "Sortable columns" in The Component.

Pagination vs. infinite scroll vs. load more

✓ Do
