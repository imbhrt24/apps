Modals

A modal stops the whole page to demand one decision. That makes it the riskiest component you design. When a button fails, one action is lost. When a modal fails, a keyboard user is locked out of the page, or trapped behind it.

You already know this

A modal needs a way out and it needs to fit the screen. Both sound obvious and both are regularly shipped broken.

An obvious way out

If the only exit is clicking the dimmed area outside, a keyboard user has no exit at all, and many mouse users never discover it. Every modal needs a visible close control that can be reached and pressed.

Every modal gets a close button in the same corner, at least 24 px and ideally 44 px on touch, with the name "Close". Add a text action such as "Cancel" or "Got it" as well.

WCAG 2.1.1 Keyboard (A) and 2.1.2 No Keyboard Trap (A): if focus can enter, the person must be able to leave with the keyboard. Close button target: 2.5.8 (AA).

It fits small screens and zoomed text

A 480 px modal designed on a large monitor meets a 375 px phone, or a user at 200% zoom, and the buttons fall off the bottom of the screen. People with low vision zoom all the time. To them, your desktop layout is a phone layout.

What you're probably missing

You cannot see any of this in a mockup. It is all about where the keyboard focus is, and what a screen reader is told.

The focus journey: in, stay, out, back

This is the single most important thing about modals. Four things must happen, in order: focus moves into the modal, Tab stays inside it, Esc closes it, and focus goes back to where you were. Miss one and keyboard users are lost.

  • Focus moves into the modal
  • Tab stays inside the modal
  • Esc closes it
  • Focus returns to the button
  • Focus moves into the modal
  • Tab stays inside the modal
  • Esc closes it
  • Focus returns to the button

Use the keyboard only. Open each modal with Enter, press Tab five or six times, then press Esc. The four checks under each button fill in as you go.

For each modal, annotate two things: "focus starts here" (usually the first field or the safest button) and "on close, focus returns to" (the control that opened it). If that control is gone, for example a deleted row, say where focus goes instead.

WCAG 2.4.3 Focus Order (A) and 2.1.2 No Keyboard Trap (A). A modal is the one place focus is deliberately kept in, and Esc is the way out. Developers get most of this from the native <dialog> element.

A title that is announced

When a modal opens, a sighted user sees it at once. A screen reader user hears only what the modal is told to announce. With no title they hear "dialog" and have to explore to find out why the page just changed.

Every modal gets a title, written as the question or task: "Delete Q3 report?", "Invite a teammate". Avoid "Warning" or "Are you sure?".

WCAG 4.1.2 Name, Role, Value (A). Developers give the container role="dialog" and point its name at the visible title.

The page behind is switched off

Dimming the background is only visual. If the page behind is still "live", a screen reader user swiping through content walks straight out of the modal and into the page, with the modal still covering it for everyone else.

Buttons that name the action, focus on the safe one

Wherever focus starts is what Enter will press. If that is "Delete", one stray key press destroys data. And "Yes / No" forces people to re-read the question to know which is which. That is hard at high zoom or by ear.

Senior-level traps

Each of these is a perfectly built modal used for the wrong job. This is the judgement that separates a senior designer.

Never open a modal on top of a modal

A second modal on top of the first doubles every rule above. Which one does Esc close? Where does focus return? Most products only built the logic for one layer, so the second breaks. Even when it works, people lose track of where they are.

  • Focus moves into the second modal
  • Tab stays inside the top modal
  • Esc closes only the top one
  • Focus returns to where you were
  • Focus moves into the modal
  • Tab stays inside
  • Esc closes it
  • Focus returns to the button

In both, choose "Delete account", then press Tab a few times and Esc. On the left there are two layers and the keyboard falls between them. On the right the same modal changes its content, with a Back button.

If a modal needs a follow-up question, replace its content as a second step with Back, or move the whole task to a page. Do not draw one modal over another.

Not banned by name in WCAG, but stacked modals routinely fail 2.4.3 Focus Order (A), 2.1.2 No Keyboard Trap (A) and 4.1.2 (A). The same applies to a popover or dropdown that spills outside a modal.

A long form squeezed into a modal

Enterprise tools love this: "New employee" with a dozen fields in a small box. As soon as it scrolls, the title and close button scroll away, errors appear off screen, and at 200% zoom only two fields fit.

A side panel or a full page: full height, room for errors, the page still visible for reference.

Open the modal and Tab through every field. Watch the title and the close button scroll out of view.

Rule of thumb: more than four or five fields, its own scrollbar, or a need to look at the page behind means it should not be a modal.

WCAG 1.4.10 Reflow (AA), 1.4.4 Resize Text (AA) and 3.3.1 Error Identification (A) all become hard to meet inside a small scrolling box.

A table inside a modal

"Select an account" opens a modal with a nine-column table. The table scrolls sideways, the modal scrolls up and down, and the page behind may scroll too. Two scroll areas nested in each other are disorienting for everyone. With a screen magnifier or a switch device they are close to unusable.

Modals nobody asked for

A newsletter popup three seconds after page load takes the focus away from whatever the person was reading. A screen reader user is moved mid-sentence into a dialog they did not request. The reverse also happens: a "session expiring" warning that fades away before it is noticed.

Do you need a modal at all?

Most modal problems share one fix: do not use a modal. A modal is right when the person must decide before anything else can happen. For everything else there is a calmer pattern that does not need a focus trap.

If you need to…Use this
Confirm something that can be undoneDo it, then show "Undo" in a message
Say that something workedAn inline message or a toast
Offer a few options for one itemA menu or popover next to the item
Fill in a long form, or refer to the page behindA side panel or a full page
Browse or pick from a tableA full page, or a search list
Make a serious, irreversible decisionA modal

Before drawing a modal, ask: does the rest of the page really have to stop? If not, pick from the table above.

Fewer modals means fewer chances to fail 2.4.3, 2.1.2 and 4.1.2. This is a design decision, made before any code exists.
