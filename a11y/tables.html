Tables

You scan a table with your eyes, jumping freely between rows and columns. A screen reader reads it one cell at a time, in a straight line. So the structure of the table has to carry the meaning that your eyes get for free.

You already know this

Tables are where designers shrink text and fade colours to fit more in. Readability comes first.

Readable text and rows you can follow

To squeeze in more columns, text drops to 11 px, turns grey and the row lines disappear. In a wide table the eye then slips from one row to the next halfway across. That is a real problem at high zoom, where only part of a row is visible.

Acme CorpEnterpriseActive$4,800
Globex LtdTeamPaused$900
InitechTeamActive$1,320

11 px light grey, no separators. Which amount belongs to Globex?

Acme CorpEnterpriseActive$4,800
Globex LtdTeamPaused$900
InitechTeamActive$1,320

14 px, full contrast, a line and soft banding per row.

Keep body text at 14 px or more and 4.5 : 1. Use row lines, banding, or both. If the table does not fit, remove or hide columns instead of shrinking the text.

WCAG 1.4.3 Contrast (Minimum), AA, and 1.4.4 Resize Text, AA. Row separators that carry meaning need 3 : 1 under 1.4.11.

Alignment that helps comparison

Numbers are compared by their digits, so they must line up on the right. Text is read from its start, so it lines up on the left. Centring everything looks neat and makes both jobs harder, most of all for someone magnified into one corner of the table.

Left-align text, right-align numbers, and align each header with its column. Turn on tabular (equal-width) figures in your type settings.

A readability convention rather than a WCAG criterion. It supports people with low vision and cognitive disabilities directly.

What you're probably missing

Now put the mouse down and listen to the table. These six decide whether it makes sense when read one cell at a time.

Real headers, for columns and rows

When a screen reader moves to a cell it reads the headers for that cell first: "Acme Corp, Status, Active". That only happens if the header cells are marked as headers. Bold text is not a header. Without them the user hears "Active" and has to remember which column they are in.

The top row is only bold text.

Marked column headers, and the client name heads each row.

Press "Next cell" seven or eight times in each table. On the left, "Paused" arrives with no context. On the right you always know whose status it is.

Mark two things in your spec: which row is the header row, and which column identifies each row (usually the name). Every column needs header text, including the checkbox and "Actions" columns.

WCAG 1.3.1 Info and Relationships (A). Developers use <th scope="col"> and <th scope="row">.

A title for the table

A dashboard often has three tables on one screen. Screen reader users can jump from table to table, and each one is announced by its title. Without a title they hear "table, 4 columns, 12 rows" three times.

Give every table a visible heading directly above it and note "this heading is the table's title". Include filters in it when they change the meaning: "Unpaid invoices".

WCAG 1.3.1 (A) and 2.4.6 Headings and Labels (AA). Developers use <caption> or connect the heading with aria-labelledby.

Sorting you can reach and hear

A small arrow shows you which column is sorted. Two things are usually forgotten: the header has to be a real button so the keyboard can reach it, and the sort direction has to be announced, or a blind user re-sorts in the dark.

Design three header states: not sorted, ascending, descending. Use an arrow, not just a colour. Note which columns are sortable.

WCAG 4.1.2 Name, Role, Value (A), 2.1.1 Keyboard (A) and 1.4.1 Use of Color (A). Developers set aria-sort on the header cell.

Do not merge cells

A merged header such as "Q3" spanning "Revenue" and "Cost" looks organised. For a screen reader, each cell now has two or three headers at different levels, and many screen readers read only one of them, or the wrong one.

Status by more than a coloured dot

Red, amber and green dots are the classic table status. To a colour-blind person red and green look alike, and a dot has nothing for a screen reader to read. Each one is announced as an empty cell.

Empty, loading and error states

A table with headers and nothing under them could mean three things: no data exists, it is still loading, or loading failed. A sighted user guesses. A screen reader user hears "table, 0 rows" and nothing else.

InvoiceClientAmount

Empty? Loading? Broken? It does not say.

No invoices yet
Create your first invoice to see it here.
New invoice

Words say which state this is, and what to do next.

Design four versions of every table: with data, empty, loading ("Loading invoices…") and failed ("Could not load invoices. Try again"). Also design "no results" for filters.

WCAG 4.1.3 Status Messages (AA): loading and result counts should be announced without moving focus.

Senior-level traps

Enterprise tables collect features: nested rows, hover actions, selection, endless scroll. Each one is a way to lock somebody out.

Never put a table inside a table

Line items under an invoice, sub-tasks under a task. The tempting design is a small table inside the row. A screen reader then announces the structure of both tables around every value, and the user has to keep two grids in their head at once.

Keep the table flat. Put child data in an expandable area under the row as a simple list, in a side panel, or on a detail page. If child rows need sorting or their own columns, they deserve their own page.

WCAG 1.3.1 Info and Relationships (A) and 1.3.2 Meaningful Sequence (A). The expand control is a button that reports expanded or collapsed.

Actions that only appear on hover

Hiding Edit and Delete until the mouse is over the row makes a clean table. It also hides them from everyone without a mouse: touch screens have no hover, keyboard focus is not hover, and with a screen magnifier you may never see them appear.

Show one always-visible "more actions" button per row, or keep the main action visible. If you reveal on hover, reveal on keyboard focus too, and always on touch.

WCAG 2.1.1 Keyboard (A) and 1.4.13 Content on Hover or Focus (AA).

The whole row is clickable

Clicking anywhere on a row to open it feels generous. But a row is not a control. The keyboard cannot focus it, a screen reader does not announce it as clickable, and it fights with the checkbox and buttons inside it.

Acme CorpEnterprise$4,800
GlobexTeam$900

Rows react to the mouse. There is nothing for Tab to land on.

Acme CorpEnterprise$4,800
GlobexTeam$900

The name is a link. The row can still highlight on hover as a bonus.

Pick the cell that names the row and make it the link. Style it so it reads as a link. Row hover and row click can stay as an extra for mouse users.

WCAG 2.1.1 Keyboard (A) and 4.1.2 Name, Role, Value (A).

Infinite scroll and where you are

Infinite scroll keeps adding rows as you reach the bottom. A keyboard user can therefore never Tab past the table to the footer or to the controls below it. Nobody knows how many rows there are, and after opening a row you come back to the top.

Loading more… and more… and more…Footer: Help · Contact · Export — never reached

No total, no end, and the footer keeps moving away.

1–25 of 312 invoicesPreviousNext
Footer: Help · Contact · Export

You know where you are, how much is left, and you can leave.

Use pagination or a "Load more" button. Always show the range and the total. After "Load more", say where focus goes: the first new row.

WCAG 2.1.1 Keyboard (A), 2.4.3 Focus Order (A) and 4.1.3 Status Messages (AA) for "25 more rows loaded".
