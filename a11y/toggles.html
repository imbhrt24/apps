Toggles

A toggle, or switch, turns one thing on or off, straight away. It is so small that nobody reviews it, which is why it fails in more ways than almost any other control: Is it on? Is it even a control? What did I just change?

Contrast and size again, but on a toggle the failure is specific: the off state, and the tiny knob.

The off state has to be visible too

Designers polish the "on" state in the brand colour and leave "off" as pale grey on white. Then nobody can tell whether the switch is off, disabled, or still loading. Both states need to be clearly visible as a control.

Make the whole row the target

A switch is often 30 px wide with a 12 px knob. Asking people to hit that is unkind. The fix costs nothing: let the label and the whole row toggle the switch.

Click the words or the switch. Either works.

Click the words "Location access" in both examples.

Draw the hit area as the full row height, at least 44 px on touch. Leave space between rows so neighbouring switches are not hit by mistake.

WCAG 2.5.8 Target Size (Minimum), AA: 24 × 24 CSS px. A label connected to its control extends the target for free.

What you're probably missing

A switch says only "on" or "off". Everything else, such as what it controls and that it is a switch at all, has to be designed in.

A label that is connected, not just nearby

You see "Wi-Fi" next to a switch and know they belong together. A screen reader only knows that if the two are connected in code. Otherwise it reads a settings screen as "switch, on. switch, off. switch, off."

It says what it is, and its state

A sighted user gets three facts at a glance: this is a switch, it is about dark mode, it is on. A screen reader user needs the same three. Without them they hear "button" and have to press it to find out what happens.

Dark mode

The picture changes. The announcement does not.

Name, role and state, updated on every press.

In your component notes write the three parts: name "Dark mode", type "switch", states "on / off". That is the whole brief a developer needs.

WCAG 4.1.2 Name, Role, Value (A). Developers use role="switch" with aria-checked, or a native checkbox styled as a switch.

Reach it with Tab, flip it with Space

Custom switches are often a drawing with a click attached. They never receive focus, so a keyboard user cannot change the setting at all. No drag gesture should be required either.

Put the mouse down. Try to change "Autoplay videos" in both panels using only Tab and Space.

Add a focus variant to the switch component. If your design allows dragging the knob, a single tap or key press must do the same thing.

WCAG 2.1.1 Keyboard (A), 2.4.7 Focus Visible (AA) and 2.5.7 Dragging Movements (AA).

Name the thing, not the action

"Disable notifications: on." Are notifications on or off? A label that describes an action, or uses a negative, turns every switch into a logic puzzle. Name the feature and let the switch say on or off.

Read each label followed by "is on". "Notifications is on" works. "Disable notifications is on" does not. Also keep the label fixed: it should not change text when toggled.

WCAG 3.3.2 Labels or Instructions (A) and 2.4.6 Headings and Labels (AA).

Senior-level traps

The switch itself is fine. The mistake is using a switch here at all, or forgetting what happens after it flips.

Switch or checkbox?

A switch means "this happens now", like a light switch. A checkbox means "this is my choice, apply it when I press Save". Put a switch inside a form with a Save button and nobody knows whether it has already taken effect.

Public profile
Save changes

Is the profile public already, or only after Save?

Save changes

A checkbox is a choice. Save applies it. No ambiguity.

Rule of thumb: instant effect, use a switch. Needs Save, use a checkbox. One of several options, use radio buttons.

A convention rather than a WCAG criterion, but it protects 3.2.2 On Input (A): changing a setting should never do something the person did not expect.

Instant changes still need confirmation

Flipping a switch usually saves something on a server. That can take time, or fail. If the switch simply moves, nobody knows whether the change stuck, and a silent failure that flips it back is worse.

It moves. Did it save? If the save fails, will anyone be told?

"Saving…" then "Saved" appears as text, and is announced.

Design three moments: saving, saved, and failed. For failed, write the message and show the switch returning to its old position with an explanation.

WCAG 4.1.3 Status Messages (AA) and 3.3.1 Error Identification (A).

A switch between two options

"Monthly [switch] Yearly." Which side is selected? A switch has one label and two states, on and off. Use it to pick between two things and neither sighted users nor screen readers can say which is chosen.

MonthlyYearly

"On" means… yearly? The highlighted side? Nobody knows.

Two named options. The chosen one is filled, bold and announced.

If you can label both ends, it is not a switch. Use a segmented control, tabs or radio buttons.

WCAG 4.1.2 Name, Role, Value (A) and 1.3.1 (A). A two-option choice is a radio group.

No surprises when it flips

A switch should change one setting and nothing else. If flipping it opens a setup flow, jumps to another page or submits a form, the person has lost their place. For a screen reader user the whole page just changed under them.
